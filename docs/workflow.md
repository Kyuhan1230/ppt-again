# 보고 자료의 수정과 인계

## 해결하려는 문제

장표를 만드는 일은 첫 화면을 완성하는 데서 끝나지 않습니다. 검토자가 표현을 고치고, 숫자가 바뀌고, 다음 담당자가 자료를 이어받습니다. HTML로 만든 결과가 보기 좋아도 받는 사람이 수정할 수 없다면 작성자에게 작업이 돌아옵니다.

Slidehandoff는 이 마지막 전달 과정에 집중합니다. 작성자는 HTML을 계속 다루고, 받는 사람은 PowerPoint에서 필요한 부분을 고칠 수 있게 합니다. 아래 상황은 제품을 설계할 때 정한 사용 가설이며, 고객 인터뷰 결과가 아닙니다.

| 상황 | 필요한 결과 | 확인 방법 |
| --- | --- | --- |
| 보고 직전에 숫자가 바뀐다 | 해당 숫자를 PPT에서 바로 고친다 | 텍스트 수정 후 저장하고 다시 열기 |
| 동료가 자료를 이어받는다 | 작성자의 도구 없이 문구와 도형을 수정한다 | 인수자가 설명 없이 후속 작업 수행 |
| 매주 보고 내용을 바꾼다 | 수정한 HTML을 다시 출력해도 나머지가 유지된다 | 수정 전후의 비대상 글자·객체 비교 |
| 회사 자료를 사용한다 | 처리 위치와 보관 범위를 이해한다 | 통신·접근·삭제 동작과 안내 대조 |

## 선택한 방식과 그 이유

**입력은 HTML, 전달은 PPT로 정했습니다.** HTML 작성 방식을 강요하지 않으면서 받는 사람이 익숙한 도구에서 후속 수정을 할 수 있게 하려는 선택입니다. PPT에서 고친 내용을 HTML에 되돌리는 기능은 없습니다.

**글자와 기본 도형은 각각의 객체로 만듭니다.** 장표 전체를 한 장의 이미지로 저장하면 모양은 비슷해도 수정과 인계라는 목적을 충족하지 못합니다. 대신 브라우저와 PowerPoint의 글꼴·줄바꿈 차이를 해결해야 합니다. 복잡한 그림의 내부 편집까지 약속하지 않습니다.

**처리는 로컬에서 시작합니다.** 문서를 외부 변환 서버에 보내지 않는 구조를 택했습니다. 그만큼 설치 환경과 글꼴의 차이를 안내해야 합니다. 로컬 실행만으로 문서 보호가 완료된 것은 아니므로 접근과 보관 문제를 별도로 확인합니다.

## 효과를 확인하는 기준

아직 시간 절감이나 구매 의향을 측정하지 않았습니다. 사용자 확인 단계에서는 변환 시간만 재지 않습니다. HTML 준비, 변환 실패 대응, PPT 확인과 재작업을 포함한 전체 시간을 기존 방식과 비교할 계획입니다.

초기 확인 항목은 작업 완료 여부, 내용 누락, 수정 가능한 객체, 인수자의 후속 수정, 재작업 시간입니다. 빠르더라도 누락이 생기거나 받는 사람이 수정할 수 없다면 개선이라고 판단하지 않습니다.

## 프로젝트로 남기려는 근거

업무 개선은 기능을 많이 만드는 것보다 문제와 효과를 설명할 수 있어야 합니다. 이 프로젝트에서는 수정·인계라는 문제를 좁히고, 파일 형식의 차이와 문서 보호를 설계에 반영하며, 확인한 범위와 남은 한계를 구분하는 과정을 남깁니다. 실제 도입 성과나 업무 효율 향상은 사용자 작업을 측정한 뒤 기록합니다.
